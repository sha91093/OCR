## 1. プロジェクト概要と設計目標

本ツールは、紙ベースの申請書をスキャンした画像・PDFからOCRによってテキストを抽出し、CSVまたはExcel形式で出力するデスクトップアプリケーションである。

### 設計における最優先事項

| 優先度 | 項目 | 理由 |
|--------|------|------|
| 1 | 低スペックPC対応 | 行政・中小企業の現場では旧型PCが多く、RAM 4GB・Core i3 程度の環境が想定される |
| 2 | 日本語OCR精度 | 申請書の縦書き・横書き混在、旧字体・手書きへの対応が必須 |
| 3 | 操作の簡便性 | ITリテラシーが高くないエンドユーザーでも直感的に操作できるUI |
| 4 | 保守性 | 将来的な機能追加・OCRエンジン差し替えに耐えられるモジュール設計 |

## 2. アーキテクチャ設計

### 2.1 全体構成: 階層型アーキテクチャ

```
┌─────────────────────────────┐
│         UI 層 (src/ui)       │  Tkinter ウィンドウ・ダイアログ
├─────────────────────────────┤
│      ビジネスロジック層       │  OCR処理・前処理・エクスポート
│       (src/core)            │
├─────────────────────────────┤
│     ユーティリティ層         │  ファイル操作・ログ・バリデーション
│      (src/utils)            │
├─────────────────────────────┤
│      インフラ層              │  SQLite DB・ファイルシステム
└─────────────────────────────┘
```

**決定理由:**
MVC・MVVMといった複雑なパターンは小規模ツールにはオーバーエンジニアリングになる。シンプルな階層分離を選択することで、チームの学習コストを抑えつつ、テスト容易性を確保した。

## 3. 技術選定の根拠

### 3.1 OCRエンジン: ndlocr-lite

**採用理由:**
- 国立国会図書館が開発した日本語特化OCRエンジンであり、縦書き・横書き混在文書への対応が他エンジンより優れている
- 旧字体・変体仮名の認識にも対応しており、古い申請書様式への対応が可能
- オープンソースであり、ライセンスコストが発生しない

**代替検討:**
- Tesseract OCR: 多言語対応だが日本語精度が劣る。縦書きのサポートが不完全
- PaddleOCR: 中国語起源のため日本語固有文字の精度に懸念
- Google Cloud Vision API: クラウド依存となりオフライン環境・機密文書に不向き

**リスク:**
- ndlocr-lite は更新頻度がやや低く、Python バージョン対応が遅れる可能性がある
- 将来的なエンジン差し替えを考慮し、`OcrEngine` インターフェースを定義してアダプターパターンで抽象化する予定

---

### 3.2 GUIフレームワーク: Tkinter

**採用理由:**
- Python 標準ライブラリに同梱されており、追加インストール不要
- 低スペックPCでのメモリ消費が最小限（PyQtやwxPythonと比較して軽量）
- 依存関係がシンプルであり、配布・インストールが容易

**代替検討:**
- PyQt5/PySide6: 高機能だが商用ライセンスの懸念あり、インストールサイズも大きい
- tkinter + ttkbootstrap: テーマ拡張ライブラリ。採用を検討中だが依存追加になるため保留
- Dear PyGui: 高性能だが学習コストが高く、既存Tkinter知識を活かしにくい

**制約:**
- 複雑なアニメーション・カスタムレンダリングには向かないが、本ツールの要件では十分

---

### 3.3 データストア: SQLite

**採用理由:**
- サーバー不要のファイルベースDB。インストール・設定作業が不要
- Python 標準ライブラリ (`sqlite3` モジュール) に含まれており、外部依存なし
- 低スペックPC環境でも軽量動作。PostgreSQL/MySQLは過剰スペック
- 処理履歴・テンプレート設定の永続化に使用する

**データベースファイルの配置:**
- `~/.ocr_shinseisho/ocr_shinseisho.db` に配置
- システムディレクトリへの書き込み権限がない制限ユーザー環境でも動作するため、ホームディレクトリ配下を選択

---

### 3.4 画像前処理: OpenCV (headless版)

**採用理由:**
- `opencv-python-headless` はGUI描画ライブラリ (Qt, GTK等) への依存を排除した軽量ビルド
- 通常版 `opencv-python` と比較してインストールサイズが約40%削減
- 本ツールは Tkinter を使用するため OpenCV の GUI 機能は不要

**前処理パイプライン設計 (予定):**
1. グレースケール変換
2. ノイズ除去 (ガウシアンフィルタ)
3. 大津の二値化 (Otsu's thresholding)
4. 傾き検出・補正 (Hough変換)
5. 解像度正規化 (300DPI相当にリサイズ)

---

### 3.5 CSV出力: BOM付きUTF-8 (`utf-8-sig`)

**採用理由:**
- 出力されたCSVを Excel で開いた際の文字化けを防ぐため、BOM付きUTF-8 を標準採用
- 日本の行政・ビジネス現場では Excel での確認が一般的であり、ユーザビリティを優先した

## 4. 低スペックPC対応のための設計判断

### 4.1 メモリ管理

- OCR処理は1枚ずつ逐次処理 (`BATCH_SIZE = 1`) とし、複数画像の同時メモリ展開を避ける
- 高解像度画像は処理前に `MAX_IMAGE_WIDTH / MAX_IMAGE_HEIGHT = 4096px` に制限してリサイズ
- PDFのDPIは300に固定（400DPI以上はメモリ消費が急増するため）

### 4.2 UIのレスポンシブ性

- OCR処理は `threading.Thread` でバックグラウンド実行し、UI がフリーズしないようにする
- プログレスバーダイアログで処理状況をユーザーに伝える
- 処理中はキャンセルボタンを提供し、長時間処理を中断可能にする

### 4.3 起動時間の最適化

- 重量級ライブラリ (ndlocr, OpenCV) は実際の処理が発生する際に遅延インポート (lazy import) する
- 設定ファイルの読み込みは起動時に1回だけ実施し、キャッシュする

## 5. テスト戦略

### 5.1 ユニットテスト

- 画像前処理関数、CSVエクスポート関数、バリデーション関数を対象とする
- OCRエンジン部分はモック化してテスト実行時間を短縮する

### 5.2 結合テスト

- サンプル申請書画像を使用したエンドツーエンドのOCRフロー検証
- `tests/fixtures/` にテスト用サンプル画像を格納する

### 5.3 カバレッジ目標

- コアロジック層 (`src/core`) は 80% 以上のカバレッジを維持する
- UI層は手動テストを補完的に実施する
