#### 2-2. DPI座標スケーリング結合（木村 / 佐藤）

**木村**: `field_editor.py` 側で対応した内容を報告します。
これまで PDF プレビュー時の解像度が `mat = fitz.Matrix(1.56, 1.56)` という
マジックナンバーで書かれていました。今回 `PREVIEW_DPI = 150` という定数を定義し、

```python
_scale = PREVIEW_DPI / 72.0   # PyMuPDF のベースDPIは 72
mat = fitz.Matrix(_scale, _scale)
```

と計算式に変えました。フィールド保存時には `template_dpi: PREVIEW_DPI` も一緒に
DB に記録するようにしています。

**佐藤**: バックエンド側の対応です。`database.py` の `form_fields` テーブルに
`template_dpi INTEGER NOT NULL DEFAULT 150` カラムを追加しました。
既存の DB ファイルに対しては `PRAGMA table_info` でカラムの有無を判定し、
未追加なら `ALTER TABLE` で自動追加するマイグレーション処理も `initialize_db()` に組み込みました。

そして `ocr_processor.py` に `_scale_fields_for_dpi()` メソッドを追加しました。
OCR 処理前に呼び出され、`template_dpi ≠ processing_dpi` の場合に座標を変換します。

```
scaled_coord = original_coord × (processing_dpi / template_dpi)
```

例：template_dpi=150、processing_dpi=300 のとき座標は2倍にスケールされます。

**渡辺**: これは重要な修正ですね。高解像度で OCR すると精度が上がりますが、
フィールド定義は低解像度プレビューで行うため、変換なしでは座標がずれていました。
今後 `dpi=300` の OCRProcessor インスタンスを使っても問題なく動作しますね。

**中村**: `_scale_fields_for_dpi()` のテストも `test_converters.py` の `scale_coords`
テストでカバーされていますが、`ocr_processor.py` の結合テストもあった方が安全です。
次フェーズで追加しましょう。

#### 2-3. Windows パッケージング設定（渡辺）

**渡辺**: `ocr_shinseisho.spec` と `build_windows.bat` を作成しました。
PyInstaller の **onedir モード**（ディレクトリ形式）を採用しました。

| 設定項目 | 値 | 理由 |
|---|---|---|
| モード | onedir | onefileより起動が速い（展開処理なし）|
| UPX圧縮 | 有効 | ファイルサイズ削減 |
| コンソール | 非表示 | GUI専用アプリのため |
| 除外ライブラリ | numpy/pandas/requests 等 | バンドルサイズ最小化 |

**木村**: Windows での実機テストはまだですが、依存ライブラリの整理ができたのは
インストーラー作成に向けた大きな前進です。

### 3. 課題・懸念事項の共有

#### 3-1. ndlocr オフライン対応（佐藤）

**佐藤**: ndloccr はインターネット接続でモデルをダウンロードする設計ですが、
実際のユーザー環境は閉鎖ネットワーク（役所 LAN）が多いと聞いています。
モデルファイルを同梱するか、オフライン手順書を整備するかを決めたいです。

**渡辺**: ファイルサイズの問題があります。ndlocr のモデルは数GB になることもあります。
インストーラーに同梱するのは現実的ではないかもしれません。
「初回セットアップ用の内部ネットワーク中継 PC からコピーする手順」を
マニュアル化するのが現実的ではないでしょうか。

**田中**: 了解です。次フェーズのアクションアイテムに追加します。
クライアントに確認も取りましょう。

#### 3-2. 低スペックPC でのメモリ使用量（木村）

**木村**: `field_editor.py` でページ画像をキャッシュする `_page_images` 辞書が
多ページ PDF では大きくなります。現在は LRU などの上限がありません。

**佐藤**: OCR 処理側 (`pdf_processor.py`) は1ページずつ処理しているので問題ないですが、
フィールドエディタは全ページをキャッシュしています。20ページ以上の PDF が
想定されるなら上限を設けた方が安全ですね。

**中村**: 上限付きキャッシュの実装と、それに対応するテストを次フェーズに追加します。

#### 3-3. `ocr_processor.py` 結合テスト不足（中村）

**中村**: DPI スケーリング含め `OCRProcessor.process_file()` の結合テストが
現状ありません。モックの OCR エンジンを使った統合テストを書く必要があります。

**田中**: 優先度高ですね。Phase 4 の開始前に追加してください。
